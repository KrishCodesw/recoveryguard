# RecoveryGuard Glossary

| Term | Meaning |
|---|---|
| Agent | RecoveryGuard process that runs near the customer Kafka cluster and collects evidence. |
| Baseline | Evidence collected before an incident. A baseline is required for claims that compare pre-incident and post-recovery state. |
| Broker | A Kafka server that stores and serves partition data. |
| Bootstrap server | An initial Kafka endpoint used by a client to discover cluster metadata and broker endpoints. |
| Cluster identity | Stable RecoveryGuard identity assigned to a registered Kafka deployment. |
| Collection run | One bounded execution of an evidence collection plan. |
| Consumer group | Kafka mechanism that coordinates consumers that share partitions. RecoveryGuard must not join a group. |
| Evidence | A timestamped observation, source record, or customer-provided artifact used by a validation check. |
| Evidence bundle | A versioned collection of evidence, metadata, hashes, check results, and verdict details for a validation run. |
| Evidence completeness | Whether the required evidence fields and sources are present for a check. |
| Evidence freshness | Whether evidence is recent enough for the check's stated time window and policy. |
| Ground truth | An independently established expected outcome used to score RecoveryGuard in the Lab. It must not be generated by RecoveryGuard's validation code. |
| High-watermark (HW) | The offset boundary for records replicated to all current in-sync replicas. |
| Incident window | The time range that RecoveryGuard uses to group pre-event, failure, and post-recovery evidence. |
| In-sync replica (ISR) | A replica that is currently considered caught up enough to participate in the partition's in-sync replica set. |
| Leader | The broker that serves reads and writes for a partition. |
| Log end offset (LEO) | The offset of the next record to be written at the end of a replica's log. |
| Offset | A record position within a Kafka partition. Offsets are not a universal count of business events. |
| Observer effect | Changes in target system behaviour caused by RecoveryGuard's own requests or resource use. |
| Partition | An ordered, replicated log within a Kafka topic. |
| Required check | A check whose outcome is needed for the configured validation decision. |
| Optional check | An advisory check that adds context but does not block a verdict by itself. |
| Recovery | Kafka or platform actions that restore service after a failure. |
| Recovery correctness | Whether the observed post-recovery state satisfies the explicitly configured correctness conditions. |
| Site | Customer-side RecoveryGuard control, evidence, validation, and reporting deployment. |
| Snapshot | A timestamped, bounded observation of cluster or resource state. |
| Verdict | The outcome produced by the validation policy for a specific evidence set and scope. |
| Validation scope | The exact cluster, resources, time window, and classes of correctness that a verdict covers. |

## Important interpretation rules

- An offset gap does not automatically prove data loss.
- A successful broker recovery does not automatically prove application correctness.
- A missing baseline can prevent a data-preservation claim.
- Evidence hashes check payload integrity; they do not prove that the source told the truth.
- A verdict applies only to its stated scope, checks, evidence, and versions.
